# Data Models

Mongoose models live in `src/backend/integrations/database/models/`. Repositories are the
only code that imports them directly (see `docs/architecture.md`). Every repository function
must call `getMongoConnection()` (`src/backend/integrations/database/connection.ts`) before
touching a model — models do not connect themselves.

## Subscriber

File: `src/backend/integrations/database/models/Subscriber.ts`
Collection: `subscribers`
Repository: `src/backend/features/subscribers/subscriber.repository.ts`

Stores stay-tuned/waitlist signups from the public interest form (`POST /api/stay-tuned`).

| Field | Type | Constraints |
| --- | --- | --- |
| `name` | `String` | required, trimmed, 2–100 chars |
| `email` | `String` | required, unique, trimmed, lowercased, email-shaped |
| `discountCode` | `String` | required; generated by `subscriber.service.ts`, reissued on every re-submission |
| `count` | `Number` | default `1`, min `1`; incremented each time the same email re-submits |
| `createdAt` / `updatedAt` | `Date` | from `timestamps: true` |

Indexes: `{ email: 1 }` (also enforces uniqueness), `{ createdAt: -1 }` (admin listing order).

Persistence is an atomic upsert (`findOneAndUpdate` with `upsert: true`) keyed on `email`,
so concurrent submissions for the same new address cannot race into a duplicate-key error.

## SiteSettings

File: `src/backend/integrations/database/models/SiteSettings.ts`
Collection: `sitesettings`
Repository: `src/backend/features/settings/settings.repository.ts`

Single-document collection holding site-wide configuration.

| Field | Type | Constraints |
| --- | --- | --- |
| `theme` | `String` | required, default `'sorvene'` (see `src/common/themes.ts`) |
| `createdAt` / `updatedAt` | `Date` | from `timestamps: true` |

`settings.service.ts#getTheme` tolerates a missing/unreachable database (build phase, unset
`MONGODB_URI`, or a connection failure) by falling back to `DEFAULT_THEME` rather than failing
the request.

## Category

File: `src/backend/integrations/database/models/Category.ts`
Collection: `categories`
Repository: `src/backend/features/catalog/catalog.repository.ts`

Storefront taxonomy for organizing products (a product can belong to many categories).

| Field | Type | Constraints |
| --- | --- | --- |
| `name` | `String` | required, trimmed, ≤120 chars |
| `slug` | `String` | required, unique, lowercased, generated from `name` (suffixed on collision) |
| `description` | `String` | optional, default `''`, ≤600 chars |
| `imageUrl` | `String` | optional, default `''`; public R2 URL set via `/api/admin/media` |
| `isActive` | `Boolean` | default `true`; hidden categories are excluded from the storefront |
| `createdAt` / `updatedAt` | `Date` | from `timestamps: true` |

Indexes: `{ slug: 1 }` (unique), `{ isActive: 1 }`.

Deleting a category also `$pull`s its id from every product's `categories` array.

## Product

File: `src/backend/integrations/database/models/Product.ts`
Collection: `products`
Repository: `src/backend/features/catalog/catalog.repository.ts`

Storefront product. References `categories` and `collections` as many-to-many ObjectId arrays.

| Field | Type | Constraints |
| --- | --- | --- |
| `name` | `String` | required, trimmed, ≤160 chars |
| `slug` | `String` | required, unique, lowercased, generated from `name` |
| `description` | `String` | required |
| `price` | `Number` | required, ≥0 |
| `compareAtPrice` | `Number` | optional, default `null`, ≥0; used for "was" price display |
| `images` | `[String]` | default `[]`, ≤12; public R2 URLs |
| `categories` | `[ObjectId ref Category]` | default `[]`; many-to-many |
| `collections` | `[ObjectId ref Collection]` | default `[]`; many-to-many |
| `status` | `String` | enum `draft` / `active`, default `draft`; only `active` is shown on the storefront |
| `featured` | `Boolean` | default `false`; featured-first default sort |
| `materialInfo` | `String` | optional, default `''`, ≤500; shown on the product detail page |
| `manufacturingInfo` | `String` | optional, default `''`, ≤500; shown on the product detail page |
| `stockQuantity` | `Number` | default `0`, ≥0 integer; internal-only — never returned by storefront APIs |
| `createdAt` / `updatedAt` | `Date` | from `timestamps: true` |

Indexes: `{ slug: 1 }` (unique), `{ status: 1, featured: -1, createdAt: -1 }`.

The service validates that every `categories`/`collections` id exists before persisting, so
products cannot reference a deleted taxonomy.

## Customer

File: `src/backend/integrations/database/models/Customer.ts`
Collection: `customers`
Repository: `src/backend/features/customer/customer.repository.ts`

Storefront shopper, identified by their phone number (E.164). Created during checkout when a
WhatsApp-delivered OTP is first verified (`POST /api/customer/otp/verify`).

| Field | Type | Constraints |
| --- | --- | --- |
| `phone` | `String` | required, unique, trimmed; E.164 (e.g. `+919876543210`) |
| `name` | `String` | optional, trimmed |
| `email` | `String` | optional, trimmed, lowercased, email-shaped; sparse unique index (multiple customers may omit email) |
| `profilePicUrl` | `String` | default `''`; public R2 URL set via `POST /api/customer/me/avatar` |
| `wishlist` | `[String]` | default `[]`; product slugs the customer wishlisted (see the wishlist feature) |
| `addresses` | `[Address]` | default `[]`; shipping addresses as subdocuments (see below) |
| `createdAt` / `updatedAt` | `Date` | from `timestamps: true` |

Address subdocument (`_id` is generated per address):

| Field | Type | Constraints |
| --- | --- | --- |
| `fullName` | `String` | required, trimmed |
| `phone` | `String` | required, trimmed |
| `line1` | `String` | required, trimmed |
| `line2` | `String` | optional, default `''` |
| `city` | `String` | required, trimmed |
| `state` | `String` | required, trimmed |
| `pincode` | `String` | required, trimmed |

Indexes: `{ phone: 1 }` (also enforces uniqueness), plus a sparse unique index on `email`.

Persistence is an atomic upsert (`findOneAndUpdate` with `upsert: true`) keyed on `phone`,
so concurrent first-time sign-ins for the same number cannot race into a duplicate-key error.
Addresses are appended with `$push`; the newest address is the last element. The wishlist is
a list of product slugs persisted by the wishlist feature (`src/backend/features/wishlist`).

## Order

File: `src/backend/integrations/database/models/Order.ts`
Collection: `orders`
Repository: `src/backend/features/orders/orders.repository.ts`

A placed order. Created by `POST /api/customer/orders`; admin viewing happens via
`GET /api/admin/orders`.

| Field | Type | Constraints |
| --- | --- | --- |
| `number` | `String` | required, unique; human order number (e.g. `SR-YYYYMMDD-XXXX`) |
| `customerId` | `ObjectId ref Customer` | required |
| `customerPhone` | `String` | snapshot of the customer's phone at order time |
| `address` | `Address` subdocument | snapshot of the delivery address |
| `items` | `[OrderItem]` | array of line items (see below) |
| `subtotal` | `Number` | sum of line totals, computed server-side |
| `total` | `Number` | equals `subtotal` (no shipping/payment implemented yet) |
| `status` | `String` | enum `placed`, default `placed` |
| `createdAt` / `updatedAt` | `Date` | from `timestamps: true` |

OrderItem subdocument:

| Field | Type | Constraints |
| --- | --- | --- |
| `slug` | `String` | required; product slug at order time |
| `name` | `String` | required; snapshot |
| `price` | `Number` | required; snapshot (server-side, never client-supplied) |
| `image` | `String` | snapshot of the first product image |
| `quantity` | `Number` | required, integer ≥1 |
| `lineTotal` | `Number` | `price × quantity` |

Indexes: `{ number: 1 }` (unique), `{ customerId: 1 }`, `{ createdAt: -1 }`.

Prices are always resolved server-side from the catalog; the client only submits slugs and
quantities. Products with a positive `stockQuantity` are checked and atomically decremented
when an order is placed, so stock cannot be oversold.

## OtpChallenge

File: `src/backend/integrations/database/models/OtpChallenge.ts`
Collection: `otpchallenges`
Repository: `src/backend/features/customer/otp.repository.ts`

Short-lived challenge for WhatsApp OTP sign-in. One active challenge per phone; the code is
stored only as an HMAC hash (keyed by `CUSTOMER_SESSION_SECRET`), never in plaintext.

| Field | Type | Constraints |
| --- | --- | --- |
| `phone` | `String` | required, unique, trimmed; E.164 |
| `codeHash` | `String` | required; HMAC-SHA256 hash of `phone:code` |
| `attempts` | `Number` | default `0`; incremented per wrong code, capped at 5 by the service |
| `expiresAt` | `Date` | required; TTL index (`expireAfterSeconds: 0`) auto-deletes expired rows |
| `lastSentAt` | `Date` | required; drives the 30s resend cooldown |
| `createdAt` / `updatedAt` | `Date` | from `timestamps: true` |

Indexes: `{ phone: 1 }` (unique — one active code per number), `{ expiresAt: 1 }` TTL.

## Adding a new model

1. Define the schema in `backend/integrations/database/models/<Name>.ts`, exporting the
   compiled model (`mongoose.models.X || mongoose.model(...)`) to survive hot reload.
2. Add a repository module that calls `getMongoConnection()` before every query.
3. Document the model here: fields, constraints, indexes, and any non-obvious persistence
   behavior (atomic upserts, soft deletes, etc.).
